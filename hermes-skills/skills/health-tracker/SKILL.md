# Здоровье: метрики, лекарства, анализы

Хаб по здоровью. Питание — `nutrition`, cron-брифы — `health-reminder`, импорт медицинских PDF/фото — `medical-import`.

Перед первым запуском собственного Python, диагностикой или тестами прочитай файловым инструментом `/opt/data/home/python-runtime.md`. Перед правкой заметок загрузи `notes-vault` и прочитай `/notes/AGENTS.md`.

## Где что лежит

```bash
PY=/opt/data/home/.venv/bin/python
CLI=/opt/data/skills-custom/health/health-tracker/scripts/health.py
DB=/opt/data/personal/health/health.db          # данные, НЕ внутри скилла
DOCS=/opt/data/personal/health/documents        # originals документов
```

Obsidian (`/notes/Моё здоровье/`) — источник правды для схемы и целей; SQLite — реплика/fallback:
- `Схема препаратов.md` — frontmatter `medications:` (слоты `morning`, `lunch`, `evening`, `as_needed`, а также legacy-слот `wednesday_morning` для обратной совместимости);
- `Цели и мониторинг.md` — frontmatter `targets:` (ккал/БЖУ) и необязательный `monitoring:` (личные коридоры веса/сахара/давления, вода, замеры, панель анализов — читает `/opt/data/scripts/health_monitoring.py`);
- `Расписание и план обследований.md`, `Динамика анализов.md`, `Фокус недели.md`, `Исследования/`.

`/opt/data/scripts/health_sync.py` реплицирует Obsidian → `health.db` (`medications`, `profile`) и при ошибке разметки отдаёт `sync_warnings`. Работа с заметками — по навыку `obsidian`.

Схема БД: `references/db-schema.md`.

## Метрики

Записывать только через CLI (время MSK ставится само):

```bash
$PY $CLI metric weight --value 82.4               # weight|glucose|pulse|waist|temp|water|sleep|steps|active_cal
$PY $CLI metric bp --systolic 128 --diastolic 82   # давление: только systolic/diastolic, без --value
$PY $CLI list --date YYYY-MM-DD             # детальный список
$PY $CLI list --date YYYY-MM-DD --summary   # машинная сводка: {"status": "ok", "has_records": bool, "count": N}
```

«Сахар» → `type='glucose'`. Единицы по умолчанию проставляет CLI.

Проверка наличия записей за период без вывода raw записей выполняется через `$PY $CLI list --date YYYY-MM-DD --summary` (агрегаты остаются персональными данными). В рамках проверки за запрошенный период после получения достаточного машинного результата (`has_records`, `count`) не делать необоснованных повторных чтений, запросов соседних дат и чтения исходников скриптов; новые явные задачи пользователя, сравнение периодов, обоснованная диагностика реальных сбоев и проверка после разрешённых исправлений не запрещены. При ошибке БД выводится честная ошибка схемы/БД с ненулевым exit code без маскировки под отсутствие данных и без обхода защит.

Исправление: показать строки `SELECT id, date, ts, type, value, unit, systolic, diastolic FROM metrics ...`, получить подтверждение, `UPDATE` только по точным `id`, проверить результат.

## Лекарства

Схему меняем в Obsidian (`Схема препаратов.md`), не в БД:
1. Править frontmatter `medications:` (слоты: `morning`, `lunch`, `evening`, `as_needed`; `wednesday_morning` поддерживается исключительно для совместимости с legacy-схемами еженедельного приёма и не является универсальным расписанием) и описание в тексте заметки, обновив `updated: YYYY-MM-DDTHH:mm:ss`. Каждому препарату указывать `food` (`before` / `with` / `after` / `any`). Перенос стимулирующих добавок (адаптогены, ноотропы) из `evening` в более ранние слоты защищает ночной сон от перевозбуждения ЦНС; препараты `lunch` с `food: with/after` автоматически подтягиваются в дневные напоминания при записи еды (12:00–18:00).
2. Сразу вызвать `$PY /opt/data/scripts/health_sync.py`, чтобы реплицировать изменения в таблицу `medications` в `health.db` и убедиться в отсутствии `sync_warnings`.
3. Проверить результат через `$PY $CLI meds-catalog --text`.

Отметка приёма — **по каждому препарату**:

```bash
$PY $CLI take-meds                                   # «принял всё / таблетки выпил» — все препараты текущего слота
$PY $CLI take-meds --names "Магний"                 # «принял магний» — только названные (через запятую)
$PY $CLI take-meds --slot morning [--date YYYY-MM-DD] # явный слот/дата
$PY $CLI medication --name "Название"              # разовый приём препарата вне схемы (по потребности)
```

- Владелец назвал конкретные препараты → только `--names`, без «всех». Если указан слот, передавай одновременно `--slot` и `--names`, а не закрывай весь слот. Названия можно разговорные («магний», «омегу») — CLI сопоставит. Если одно имя назначено в нескольких слотах, сначала установи слот по явным словам владельца или уточни; не выбирай другую непринятую дозу при повторном подтверждении, поскольку повтор сообщения не доказывает новый приём.
- «Принял всё» (без `--names` и `--slot`) работает по тем же окнам, что и напоминания (ниже): отмечает всё непринятое в текущем окне; пропущенное раньше не трогает. Пустое окно — не ошибка, в ответе подсказка про запись по названию.
- Препарат, названный владельцем (`--names`), записывается в любое время суток, без ограничений окна, в своём слоте из схемы (утренний препарат, отмеченный вечером, → слот morning). Позднюю дозу владелец решает сам после консультации с врачом; бот не спорит и не отказывает. Препарат, которого нет в схеме на сегодня (например, еженедельный `wednesday_morning` не в среду), `take-meds --names` не найдёт (`meds_not_found`). Для разового приёма вне схемы есть `medication --name`, но при неточном названии он ждёт интерактивный ввод (`input()`): в боте запускать только с точным названием из справочника `medications`.
- **Окна напоминаний при записи еды** (`reminder_slots()` в `medication_reminder_helper.py`): до 12:00 — утренние; 12:00–16:00 — утренние + дневные вместе; 16:00–18:00 — только дневные; после 18:00 — дневные + вечерние вместе (до конца суток). Утренние после 16:00 считаются пропущенными (в «Итогах дня» и статистике видны), на вечерние не переносятся и дозу не удваиваем. Непринятые дневные дописываются к вечерним после 18:00. Слот зависит только от времени, не от числа приёмов пищи за день. Исключений по названиям препаратов нет.
- Отвечать по JSON CLI: `marked` — отмечено сейчас; `already` — уже было; `unknown` — не найдено (уточнить у владельца); `remaining` — что ещё не принято в слоте. Использовать `message`.
- Пишется в `med_intake_log` (поштучно, без дублей) и `med_log`; когда слот принят целиком — ещё и в `medication_slot_log` (старые записи слота считаются «все приняты»).
- У каждого препарата в схеме поле `food`: `before` / `with` / `after` / `any`. Новый препарат добавлять с `food`, иначе признак угадывается по `note`. `before` напоминают брифы 07:00 / 12:00 / 18:00, остальные — запись еды (`nutrition.py meal`). Логика — `/opt/data/scripts/medication_reminder_helper.py`.

Pitfalls:
- при проверке «что осталось из лекарств» сверять все незакрытые слоты дня (`lunch`, `evening`) по схеме Obsidian / `meds-catalog` с `med_intake_log`; сырой запрос к `medications` в SQLite может пропускать дневной слот;
- столбец `active`, не `is_active`;
- в таблице `medications` слот/время называется `when_text` (не `slot`); синхронизация хранит отдельную строку на имя + атомарный слот, сохраняя дозировку/food/time/note; старые объединённые строки читаются для совместимости;
- при `take-meds --names` без `--slot`, если имя есть в нескольких доступных слотах (включая принятые), CLI возвращает `requires_confirmation` / `meds_slot_ambiguous` без записи всего запроса. Уточни слот и повтори с `--slot` и `--names`; не выбирай другой непринятый слот автоматически;
- `medication` для планового препарата использует поштучный writer и поддерживает `--slot`; разовые приёмы по потребности остаются в `med_log`;
- при чтении legacy `when_text` разбирай известные значения явно: `wednesday_morning` — неделимый еженедельный слот legacy-совместимости (не универсальное расписание), а `morning_lunch` / `morning_evening` / `lunch_evening` / `morning_lunch_evening` — комбинации ежедневных слотов. Не используй произвольный `split('_')` и поиск подстроки `morning`: они теряют ограничение среды или добавляют ложный недельный приём;
- сохраняй дозировку, `food`, время и примечание отдельно для каждого слота; объединение только по имени теряет различия между утренним и дневным/вечерним приёмом. При аудите синхронизации сверяй не только названия слотов, но и все эти поля;
- кириллицу сравнивать через Python `casefold()`, не SQLite `LOWER()` и не `LIKE` (в SQLite `LIKE` нечувствителен к регистру только для ASCII; для кириллицы `LIKE` регистрозависим);
- название препарата: в `med_intake_log` и `med_log` столбец называется `medication` (не `med_name` и не `name`), а в таблице `medications` — `name`; время приёма в `med_intake_log` и `medication_slot_log` хранится в столбце `ts` (`DD.MM.YYYY HH:MM:SS`), а не `taken_at` или `created_at`.

## Справочник препаратов и опечатки

Речь и автозамена искажают названия («магнезия», «омегу», бренд вместо действующего вещества). Чтобы не угадывать, берём реальные названия из схемы (Obsidian `Схема препаратов.md`) через скрипты. Чтение справочника выполняется строго в режиме read-only (URI `mode=ro`), helper не вызывает `init_db()` и не создаёт таблицы; создание и миграция схемы вынесены в явную команду `medication_reminder_helper.py migrate`:

```bash
$PY $CLI meds-catalog --text                    # все препараты + когда принимать (утро/утро по средам/день/вечер + время/по потребности)
$PY $CLI meds-catalog                           # то же JSON (slot, time, food, dosage, note, condition)
$PY $CLI meds-resolve --query "магнезия"      # до 3 кандидатов {name, score, confident, schedule}
```

Правила:
- `take-meds --names` записывает только при надёжном совпадении с сегодняшними препаратами (`med_matches`). Если вернулся `meds_not_found`, в ответе есть `suggestions` {запрос: [{name, score, confident}]}. Сама команда по неточному названию ничего не пишет.
- `confident: true` и ясный лидер → повторить `take-meds --names "<точное название из name>"` и в ответе кратко сказать, как понял («Понял «магнезия» как Магний B6»).
- Несколько кандидатов без лидера, или `confident: false`, или пусто → не записывать, переспросить владельца со списком вариантов. Дозу и время приёма не выдумывать, брать из справочника.
- **Голосовой ввод и собирательные фразы**: распознавание речи может искажать «все лекарства / таблетки» в псевдоимена (например, «Селикатского»), совмещая со слотами («утренние вечерние принял», «проверь и запиши»). Если во фразе звучат слоты или «все»:
  1. Сначала проверь статус приёмов за сегодня (`medication_slot_log` / `med_intake_log` по названным слотам).
  2. Если часть слотов уже принята (например, утренний), а другой ожидает (вечерний) — уточни через `clarify`, подтвердив уже принятое.
  3. Для приёма слота целиком используй `take-meds --slot <morning|lunch|evening>`.
- Вопросы «когда принимать X», «что пить вечером», «что осталось принять» → отвечать строго по `meds-catalog` или схеме Obsidian (`Схема препаратов.md`), сверяя со статусом принятого за сегодня (`get_slot_status` / `med_intake_log`), а не по памяти и не прямым чтением таблицы `medications` в SQLite (при дедупликации одноимённых препаратов между утром и обедом/вечером сырой SQL может потерять дневной слот `lunch`). Проверять все оставшиеся слоты дня (`lunch`, `evening`), не перескакивая сразу на вечер.
- При вопросах о пропуске дозы или временном окончании препарата: пояснять фармакокинетику (период полувыведения, отсутствие или наличие рикошетного синдрома отмены), недопустимость удвоения следующей дозы, необходимость контроля целевых метрик (давление/пульс/глюкоза) и резервные средства из блока `as_needed` («по потребности») при ухудшении самочувствия, с дисклеймером для обсуждения с врачом.
- Справочник читает актуальную схему из Obsidian (включая `as_needed` — по потребности). Неактивные препараты из SQLite в нём не появляются.
- Схема пустая (новый владелец) — справочник пуст, напоминаний нет; предложить заполнить `Схема препаратов.md`, если владелец упоминает лекарства.

### Расчёт лекарств в дорогу и раскладка по дням

Когда владелец просит рассчитать таблетки в дорогу или дать расклад по дням:
1. Схему брать из `meds-catalog` или `Схема препаратов.md`.
2. Формат вывода — **строго хронологическая раскладка по слотам дней** (День + Слот) в fenced code block (` ```text `), чтобы удобно было раскладывать по таблетнице/отсекам:
```text
Пятница вечер (20:00, во время ужина) — N шт.:
- Название — кол-во
- ...

Суббота утро — N шт.:
- До завтрака: Название — кол-во
- Во время завтрака: Название — кол-во
- ...
```
3. Не заменять хронологический расклад абстрактным списком «всего по препаратам» — владельцу нужен конкретный порядок фасовки по дням и приёмам. Суммарный итог (сколько всего штук каждого препарата положить в дорогу) давать только как дополнение после раскладки или если был прямой запрос «сколько всего штук купить/взять».

### Расчёт дозировки новых добавок и препаратов по фото/этикетке

Когда владелец присылает фото новой банки/упаковки («смотри что приехало, сколько пить»):
1. **Масса соли vs элементарное вещество**: крупная цифра на лицевой стороне (особенно минералы: магний, цинк, железо, кальций) — это почти всегда масса соли (напр. цитрат магния 735 мг) или вес таблетки, а не чистого элемента. Всегда находить/рассчитывать долю элементарного вещества (в 735 мг цитрата — ~115 мг Mg).
2. **Личная схема против инструкции производителя**: инструкция на банке указывает общую норму производителя. Сопоставлять дозировку с текущими назначениями врача и целями в `Схема препаратов.md` и `Цели и мониторинг.md`, показывая разницу между профилактической нормой с этикетки и предписанной врачом терапевтической дозой, без самостоятельного назначения новых дозировок.
3. **Форма выпуска и синхронизация**: проверять изменение формы (капсулы vs таблетки, дозировка на штуку) и предлагать обновить запись в `Схема препаратов.md`.

## Анализы и документы

- Импорт нового PDF/фото — только по навыку `medical-import`.
- Не дубль ли документ: `references/document-dedup-check.md`.
- Ошибки OCR (HbA1c vs гемоглобин, единицы, рукопись): `references/vision-ocr-pitfalls.md`.
- Целостность связей после импорта: `$PY /opt/data/skills-custom/health/health-tracker/scripts/check_integrity.py`. Скрипт читает связи, но обычный `sqlite3.connect` может создать отсутствующую БД; не использовать как строго read-only диагностику.

## Как отвечать на вопросы

Читать `health.db` read-only, выводить кратким списком, SQL не показывать:
- «анализы» → `lab_results` по дате убыв., критические (`is_critical=1`) с ⚠️;
- «что сказал врач» → `doctor_notes` (врач, дата, заключение);
- «метрики» → `metrics ORDER BY date DESC, ts DESC` (`ts` в формате `DD.MM.YYYY` — по нему одному не сортировать);
- «документы» / «что за документ» → `documents` + связанные `lab_results`/`doctor_notes` по `document_id`.

## Исследование новых препаратов/добавок

1. Только доказательные источники (PubMed, ClinicalTrials, Cochrane, FDA/EMA, Vidal, ГРЛС) со ссылками.
2. Показатели и текущую схему брать из `Цели и мониторинг.md` и `Схема препаратов.md`, не из памяти.
3. Проверять взаимодействия с текущими препаратами и персональные риски:
   - **Фармакокинетика и ЖКТ**: оценивать влияние на моторику ЖКТ, кислотность и всасывание сопутствующих препаратов;
   - **Кардиопрофиль и вегетативный баланс**: проверять влияние на артериальное давление, сердечный ритм, риски синдрома отмены и толерантности;
   - **Влияние на сон и ЦНС**: проверять наличие стимулирующего или седативного эффекта, избегать вечернего приёма активирующих веществ и оценивать безопасность при нарушениях дыхания во сне.
4. Итог — заметка в `/notes/Моё здоровье/Исследования/<Название>.md` со статусом (`Изучается`, `Оценка совместимости`, `Тестируется`, `Внедрено`, `Отклонено`), включающая структуру: цель и механизм действия, доказательная база со ссылками, совместимость с текущей схемой, риски и противопоказания, вопросы для обсуждения с лечащим врачом.

Назначений не менять и эффект не обещать — это информация для обсуждения с врачом.

## Проверка логики лекарств

Перед изменением синхронизации, напоминаний или отметок читай `references/medication-regression-checks.md`. Успешный `meds-catalog` проверяет только чтение схемы: он не доказывает правильность SQLite-fallback, напоминаний и записи журналов. Не объявляй весь контур исправленным по одному успешному пути.

## Безопасность данных

- Любой DELETE/UPDATE медицинских записей: показать точные строки → явное подтверждение → свежая проверенная точка восстановления `personal-bot` через единый хостовый `backup-system` → изменение → read-back. Сбор и забор организует администратор на хостах по заметке `/notes/Резервное копирование.md`; бот не останавливает сам себя и не запускает отдельные копировщики БД. До подтверждения администратором снимка, покрывающего изменяемые записи, изменение блокировано. Восстановление — по `RESTORE.md` снимка, не поверх живой БД; новые записи после снимка необходимо сохранить и согласовать.
- Скрипты без `argparse` не запускать «для проверки» — сначала читать код; read-only проверка синтаксиса — `ast.parse` в памяти (`py_compile` пишет байткод).
- Python только `/opt/data/home/.venv/bin/python` (общая справка: `/opt/data/home/python-runtime.md`).

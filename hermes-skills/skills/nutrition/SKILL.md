# Питание и справочник продуктов

## Когда использовать

Запись и просмотр питания, КБЖУ и дневные цели, поиск продуктов, добавление и исправление алиасов, согласованное изменение справочника.

## Правила и запуск

- Все рабочие данные читай и меняй только через штатный CLI. Прямой SQL, импорт функций CLI и разовые скрипты к БД не разрешены без отдельно согласованного технического scope.
- КБЖУ бери из справочника, этикетки или согласованной оценки, не из головы. Не подменяй состав, жирность или способ приготовления похожим продуктом.
- Обычные добавления еды и новых алиасов выполняй без повторного подтверждения и бэкапа. Исправление истории, замена связи, удаление и изменение КБЖУ требуют согласия на точный объём; уже согласованное повторно не согласовывай.
- Проверенный receipt достаточен: не дублируй его чтением. При неизвестном результате или `saved: true, verified: false` сначала установи статус, не повторяй запись вслепую.

Команды выполняй через `terminal` с этими путями:

```bash
PY=/opt/data/home/.venv/bin/python
CLI=/opt/data/skills-custom/health/nutrition/scripts/nutrition.py
```

Для готовых CLI дополнительная runtime-справка не нужна. Перед собственным Python, диагностикой или тестами прочитай `home/python-runtime.md` (или установленную runtime-справку). Технические ограничения и тесты — `references/cli-safety-and-tests.md` (загружай по необходимости).

## 1. Запись еды

1. Определи тип: завтрак → `breakfast`, обед → `lunch`, ужин → `dinner`, перекус → `snack`. Если тип не указан, уточни через `clarify` (обычно предложи перекус). Сразу после предыдущей записи уточни: отдельный перекус или дополнение к ней; изменение уже сохранённого приёма — отдельная процедура, не молчаливое добавление.
2. Сохрани полный исходный список и названия владельца. Для каждой позиции нужен вес в граммах. Для штук/порций предложи подтверждение суммарного веса, не записывай оценку без согласия.
3. Без явной даты не передавай `--date`: CLI берёт текущую дату по Москве. Явное «вчера» или «ел до полуночи» вычисляй от свежего времени MSK. Дату из предыдущего ответа не копируй.
4. Сразу выполни `meal --json`: без предварительного поиска продуктов, проверки дубля основного приёма, чтения БД или вызова часов для обычной записи. CLI разрешает весь список до вставки. Это запись, не preview.

```bash
$PY $CLI meal --json --meal snack --items "кофе с молоком 300г, продукт 100г"
# Только для явно указанной даты добавь --date YYYY-MM-DD
```

Формат `--items`: позиции через запятую, каждая заканчивается весом `название 120г`; точку с запятой не используй. Для названия с перечислениями через запятую используй подтверждённый алиас без запятых. Десятичная запятая в жирности/весе поддерживается (`кефир 2,5% 200г`).

### Результат записи

- **`status: ok, saved: true, verified: true`**: проверь полный ожидаемый состав в receipt и ответь по `items`, `totals`, `date`, `ts`, `medication_reminder`. Проверка после commit уже выполнена CLI; повторное чтение не нужно.
- **`fuzzy_match`, `multiple_matches`, `product_not_found`**: весь приём не сохранён. Разбери все `problems`, объедини независимые вопросы о продукте, весе и источнике КБЖУ в одну форму `clarify` (до 5 вопросов). Повтори полный список только после разрешения всех проблем.
- **`additional_meal_confirmation`**: основной приём уже есть. Уточни: перекус, дополнительный основной приём или замена. Только для явно выбранного дополнительного основного приёма передай `--allow-additional`. Повторные перекусы уточнения не требуют.
- **Ошибка формата**: исправь только однозначную техническую запись формата; неоднозначный вес/название уточни.
- **Сбой проверки, таймаут или неполный receipt**: не заявляй успех и не повторяй запись. Используй доступное штатное чтение; если нужна точная проверка ID, которой нет в CLI, сообщи ограничение, не обходи его SQL.

Fuzzy-совпадение, даже единственное, требует выбора владельца. Несколько подходящих продуктов нельзя разрешать по вероятности или калориям и подставлять точное имя для обхода предупреждения. Сырой/готовый, отварной/жареный и блюда с разным составом — разные продукты.

### Ответ и лекарства

После успеха: «Записал», тип приёма, калории, краткий состав и при необходимости БЖУ. При приблизительной оценке укажи это и использованное среднее на 100 г.

Передай `medication_reminder` из receipt, если он есть; мягкие подсказки не усиливай до запретов. Расчёт напоминания может учитывать всю еду за последние 60 минут, не только текущую запись. Предупреждения stderr о сбое лекарственной подсистемы не скрывай.

Если пользователь одновременно сообщил еду и приём лекарств, загрузи `health-tracker`: запиши еду и независимо отметь лекарства через `health.py take-meds` по его правилам. Уточнение еды не должно блокировать однозначную отметку лекарств. В итоге подтверди обе операции по их фактическому статусу; исключи только что принятые препараты из напоминания. Не меняй схему или дозы.

## 2. Поиск и неизвестные продукты

Для вопроса о продукте или разрешения проблемы записи:

```bash
$PY $CLI products --query "котлеты куриные" --json
```

Поиск учитывает название и алиасы, все слова запроса, регистр, е/ё и пробелы; fuzzy-подстановки нет. `status: ok, count: 0` — совпадений нет; ошибка — не отсутствие продукта. При пустом узком поиске попробуй один значимый корень. Не выбирай автоматически из нескольких вариантов.

Неизвестный продукт разрешай так:
1. Проверь справочник через `products`. Точное соответствие используй; сомнительный эквивалент и fuzzy-вариант подтверди через `clarify`.
2. Для упаковки/этикетки загрузи `references/branded-packaged-labels.md`, для консервов также `references/canned_food_labeling.md`. Источник КБЖУ — упаковка, не интернет.
3. Без этикетки предложи данные владельца или согласованную приблизительную оценку. Перед публичным поиском загрузи `web-search-fallbacks`: только приватный SearXNG, с разрешения владельца. Выбор варианта «найти среднее в сети» в `clarify` — достаточное согласие.
4. Для домашнего блюда используй `references/generic-dish-average-fallback.md`; для обычного продукта — `references/internet-average-fallback.md`. До трёх сопоставимых источников, с оценкой надёжности.
5. Добавляй новый продукт штатной командой `product-add` (раздел ниже), только с известными КБЖУ на 100 г. Не используй прямой SQL.

### Добавление нового продукта

```bash
$PY $CLI product-add --name "Название продукта" --kcal 310.2 --protein 3.2 --fat 13 --carbs 43 --json
```

Все четыре значения на 100 г обязательны. Используй этикетку или согласованную оценку, сохраняй явно выбранное владельцем название. Если на читаемой этикетке отсутствует один из макросов (например, углеводы на мясных консервах), не подставляй `0` и не выводи его из калорийности молча — уточни через `clarify` (поставить `0`, поискать по производителю в сети или указать значение вручную). Команда добавляет только один продукт, без бэкапа и без записи еды; история и алиасы не меняются. Нормализация учитывает регистр, е/ё и пробелы. Если владелец использует короткое название, отличающееся от сохранённого брендированного имени, добавь алиас через `alias-add`.

- `created, saved: true, verified: true` — продукт сохранён; независимая post-commit проверка уже выполнена.
- `already_exists, saved: false, verified: true` — однозначный продукт с такими же КБЖУ существует, дубль не создан.
- `product_conflict`, `alias_conflict` — запись не выполнена; разбери конфликт, не перезаписывай данные и не обходи проверку другим названием.
- `verification_failed, saved: true, verified: false` — сначала проверь точный продукт через `products`, не повторяй запись вслепую.
- Отсутствующая БД или схема — ошибка, не автоматическая инициализация.

## 3. Просмотр питания и целей

```bash
$PY $CLI summary
$PY $CLI summary --date YYYY-MM-DD
$PY $CLI summary --days 7
# Только агрегаты/наличие записей, без списка блюд:
$PY $CLI summary --date YYYY-MM-DD --summary
```

При запросе «сколько съел» покажи итоговые КБЖУ и краткий состав по приёмам. Для сопоставления с заданными целями и остатка на сегодня используй `$PY /opt/data/scripts/recipe_context.py` (`today.remaining`); не вычисляй цели по памяти. При подборе еды под лекарства загрузи `health-tracker` и используй его штатные способы проверки схемы и приёмов, не читай БД напрямую.

При проверке только наличия/агрегатов достаточно `has_records` и `count` за запрошенный период. Без причины не читай исходные записи, соседние даты или исходники. Ошибку БД сообщай как ошибку, не как «записей нет».

## 4. Алиасы

### Просмотр

```bash
$PY $CLI aliases --query "чёрный хлеб" --json
# Для явно запрошенного аудита всех связей — без --query
```

`aliases` показывает сохранённые `alias → product`, `product_ids` и `dangling`. Поиск `products` не заменяет проверку связи: он может найти продукт по его собственному имени. Отсутствующая или неоднозначная цель требует разбора, не автоматической замены по похожести.

### Добавление

Добавляй полезный разговорный алиас к однозначно выбранному продукту, в том числе после подтверждения соответствия владельцем. Не создавай сомнительное соответствие и варианты, различающиеся только регистром, е/ё или пробелами.

```bash
$PY $CLI alias-add --alias "разговорное название" --id ID --json
# Вместо --id можно передать --product "Точное полное название"
```

- `created, saved: true, verified: true` — сохранено и проверено.
- `already_exists, saved: false, verified: true` — такая связь уже есть, дубль не создавался.
- `dangling_alias` — ссылка на отсутствующий продукт; `alias_conflict` — другая существующая цель. Ошибка содержит `existing`. Добавление не перезаписывает старую связь.
- Несколько разных алиасов одному продукту разрешены. Доработка команды сама по себе не разрешает менять рабочие данные.

### Исправление

```bash
$PY $CLI alias-update --alias "существующий алиас" --id ID --json
# После согласия на before → after:
$PY $CLI alias-update --alias "существующий алиас" --id ID --apply --confirm FINGERPRINT --json
```

Покажи `before → after`, затем используй точный `confirmation` preview. Уже согласованный объём повторно не согласовывай. Команда меняет только цель одной связи, не имя алиаса, продукты или историю. Успех — `status: ok, saved: true, verified: true, backup_removed: true`; CLI сам выполняет backup и post-commit проверку, дополнительных не нужно. При ошибке сообщи состояние и путь сохранённой копии; детали — `references/cli-safety-and-tests.md`.

## 5. Изменение КБЖУ и остальные исправления

```bash
$PY $CLI product-update --id ID --name "Точное название" --kcal 280 --protein 22 --json
# После согласия на before → after повтори тот же запрос с:
# --apply --confirm FINGERPRINT
```

Передавай только изменяемые поля на 100 г. Невидимые значения не выводи из калорийности и не заменяй нулями. Покажи также сохраняемые поля и сообщи, что история еды не пересчитывается. Применяй только согласованный preview с его точным `confirmation`. Критерий успеха и встроенный цикл backup/проверки такие же, как у `alias-update`.

Удаление/переименование продуктов, удаление алиасов и изменение уже записанного питания не выполняй обходными SQL-вставками. Для удаления приёма есть `delete`, но полного безопасного цикла CLI пока не обеспечивает: сначала загрузи `references/cli-safety-and-tests.md`, установи точный scope и согласуй недостающий технический способ. Без разрешённого способа резервирования и адресной проверки — остановись и сообщи ограничение.

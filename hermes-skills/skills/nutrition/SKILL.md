# Nutrition

## Когда использовать

Используй скилл, когда пользователь просит:
- записать завтрак, обед, ужин или перекус;
- показать калории или БЖУ продукта;
- показать съеденные калории, БЖУ и приёмы пищи за сегодня, конкретную дату или период;
- добавить продукт в справочник;
- исправить или удалить запись питания.

## Обязательные правила

1. Источник КБЖУ — `food_db`, точный алиас или этикетка пользователя.
2. Не считай КБЖУ из головы и не подменяй блюдо похожим по названию.
3. Для записи еды используй сразу `meal --json` с полным исходным списком, без предварительного SQL-поиска: CLI сам разрешает точные имена/алиасы до вставки. При неизвестных, похожих или неоднозначных продуктах весь приём не сохраняется; разбери все `problems`, получи выбор владельца и повтори полный список. Слепой retry запрещён.
4. Интернет используй только с разрешения пользователя и только после проверки базы и алиасов. Если поисковики блокируют бота — навык `web-search-fallbacks`.
5. Говори «записал» только при JSON `status: ok, saved: true, verified: true`: CLI уже проверил запись в `nutrition` и все позиции `nutrition_items` новым read-only соединением после commit. Отдельный SELECT после такого ответа не нужен.
6. Удаление записи требует явного подтверждения пользователя.
7. Проверка наличия записей / агрегатов за период без вывода raw записей выполняется через машинный режим `summary --summary` (или `--json`; агрегаты остаются персональными данными). В рамках проверки за запрошенный период после получения достаточного машинного результата (`has_records`, `count`) не выполнять необоснованных повторных чтений, запросов соседних дат и чтения исходников скриптов; это не запрещает новые явные задачи пользователя, сравнение периодов, обоснованную диагностику реальных сбоев или проверку после разрешённых исправлений. При ошибках БД выводить фактическую ошибку, не маскируя её под отсутствие данных и не обходя защитные механизмы.

## Формат приёма пищи

Типы:

| Пользователь | `--meal` |
|---|---|
| завтрак | `breakfast` |
| обед | `lunch` |
| ужин | `dinner` |
| перекус | `snack` |

Формат `--items`:
- продукты разделяются запятой;
- каждый элемент заканчивается весом без пробела: `название 120г`;
- точка с запятой не используется.

Пример:

```text
картошка жареная 150г, свинина жареная 200г, кофе с молоком 300г
```

Если пользователь не указал дату, **не передавай `--date` в `meal`**: CLI сам берёт текущую дату по Москве непосредственно при записи. Не копируй дату из предыдущего вызова или ответа — она может устареть после полуночи. Если дата указана явно (включая «вчера»), вычисли её от свежего системного времени в Москве и передай `--date YYYY-MM-DD`. Если владелец ел до полуночи, а пишет после — это явная дата: передай `--date` вчерашнего дня. Без явной даты используй `date` и `ts` из verified receipt: CLI вычисляет их по московскому времени при записи. Отдельный вызов часов для обычной записи не нужен; ранее сохранённую дату не подставляй.

## Главный pipeline записи

1. Определи тип приёма пищи. Дату для `--date` вычисляй только если пользователь явно указал её; иначе оставь выбор даты CLI. Если основной приём пищи (`breakfast`, `lunch`, `dinner`) за эту дату уже записан — уточни через `clarify`, записать ли его как другой приём (перекус), как дополнительный или заменить существующий. Для `snack` (перекус) повторные приёмы в течение дня нормальны и не требуют такого уточнения. Если тип приёма пищи не указан вовсе (передан только продукт и вес, например «Кефир 1% 500 г»): если сообщение пришло сразу после другой записи — уточни через `clarify`, добавить ли позицию в только что сохранённый приём или записать как отдельный перекус (`snack`); если отдельным сообщением без контекста — предложи тип приёма через `clarify` (рекомендуемый — `snack`).
2. Сохрани исходный полный список продуктов.
3. Сформируй строгую строку `--items`, сохранив названия владельца. Сразу запускай `meal --json`, без отдельного поиска продуктов и проверки наличия основного приёма: CLI делает это до вставки. Это команда записи, не read-only preview: при точном разрешении всего списка она сохраняет еду. Для вопросов о КБЖУ и поиске без намерения записать используй чтение каталога.
4. Запусти:

```bash
# Дата не указана пользователем: CLI берёт текущую дату по Москве
$PY $CLI meal --json --meal snack --items "продукт 100г, продукт 200г"

# Пользователь явно указал дату
$PY $CLI meal --json --meal snack --date YYYY-MM-DD --items "продукт 100г, продукт 200г"
```

5. Обработай результат по таблице ниже.
6. При `saved: false` разбери весь массив `problems`, а не только верхний `type`. Объедини вопросы о кандидатах в один `clarify` (до пяти за раз). Неизвестные продукты разреши по decision tree ниже. Повтори полный список только после всех уточнений, заменив подтверждённые позиции точными именами/алиасами. При `additional_meal_confirmation` уточни: перекус, дополнительный основной приём или замена; `--allow-additional` разрешён только после явного выбора дополнительного приёма. Замена требует отдельной процедуры удаления.
7. При `status: ok, saved: true, verified: true` используй receipt (`id`, `date`, `ts`, `meal`, `items`, `totals`, `medication_reminder`) без повторного SELECT. Проверь, что получен полный ожидаемый список. Напоминание передай пользователю; предупреждения stderr не скрывай.
8. При `verification_failed` (`saved: true, verified: false`), таймауте, неизвестном результате или отсутствии verified receipt сначала выясни состояние записи через read-only проверку, по известному `id` в первую очередь. Не повторяй запись вслепую и не заявляй успех. Уже сохранённое исправляй только с подтверждением.

## Обработка результата `meal`

| Результат | Действие |
|---|---|
| `status: ok, saved: true, verified: true` | Проверка после commit уже выполнена CLI; ответить по receipt без отдельного SELECT |
| `verification_failed` | Запись могла сохраниться; проверить по `id`, не повторять автоматически |
| `additional_meal_confirmation` | Получить выбор владельца; для дополнительного приёма повторить с `--allow-additional` |
| `product_not_found` | Разрешить каждый неизвестный продукт по decision tree ниже; частичную запись не считать успехом |
| `fuzzy_match` / `multiple_matches` | JSON: `status: warning`, `saved: false`, `requires_confirmation: true`, варианты в `candidates`. Весь приём не сохранён. Получить явный выбор владельца и повторить полный список с точными уникальными именами |

Код выхода 0 сам по себе не означает запись: проверяй JSON-поля. В `--json` успех — один объект receipt, без текстовой строки «Прием пищи ... записан». Текстовый режим сохранён для совместимости, но бот использует `--json`. При предупреждениях разрешения продуктов подсистема лекарств не вызывается.

### Критерий однозначного совпадения

Автоматический выбор допустим, только если одновременно выполняется всё:
- найден один подходящий кандидат;
- совпадает тип продукта или блюда;
- совпадает способ приготовления, если он указан;
- не меняется значимый состав.

Сырой, сухой, готовый, отварной и жареный варианты считаются разными. Автоматически используй только действительно однозначное точное имя или точный алиас. Несколько вариантов уже при предварительном поиске или SQL-чтении каталога требуют явного выбора пользователя ДО записи всего приёма. Не выбирай по вероятности, популярности, готовому виду или калориям и не подставляй выбранное тобой точное имя, чтобы обойти warning `meal`. Fuzzy-совпадение, даже единственное, требует подтверждения пользователя, а не автоматического исправления опечатки.

Составное блюдо нельзя выбирать по совпадению одного слова: `макароны с мясом` не равны `макаронам с сыром`.

## Decision tree для неизвестного продукта

Выполняй сверху вниз и остановись на первом подходящем варианте.

1. **Точный продукт или алиас найден** — используй его.
2. **Найден один однозначный эквивалент** — используй точное имя или подтверждённый алиас.
3. **Найдено несколько вариантов либо различаются состав/приготовление** — спроси пользователя.
4. **Пользователь дал этикетку или КБЖУ на 100 г** — добавь продукт по этим данным.
5. **Это домашнее составное блюдо без точных данных** — предложи приблизительную оценку. Выбор пользователем варианта с поиском по сети в `clarify` считается достаточным согласием. Найди 3–5 сопоставимых интернет-источников и усредни значения; подробности в `references/generic-dish-average-fallback.md`.
6. **Пользователь явно разрешил интернет-поиск для обычного продукта** — найди минимум 3 сопоставимых источника; подробности в `references/internet-average-fallback.md`.
7. **Данных всё ещё недостаточно** — запроси этикетку, КБЖУ на 100 г или уточнение варианта.

### Поиск по базе и алиасам

Не используй SQLite `LOWER()` для кириллицы. Ищи через Python `str.lower()`; подробности в `references/sqlite-cyrillic-lower-pitfall.md`.

Ищи по **одному значимому корню** или точной подстроке целиком (`'холод'`, `'кефир'`), а не по фразе с предлогами: разбиение «кофе с молоком» по словам даёт сотни ложных совпадений от «с».

```bash
$PY - <<'PY'
import os, sqlite3
q = 'НАЗВАНИЕ'.lower()
path = '/opt/data/personal/nutrition/nutrition.db'
conn = sqlite3.connect('file:' + path + '?mode=ro', uri=True)
conn.row_factory = sqlite3.Row
for table, sql in {
    'food_db': 'SELECT id, product, normalized_name, kcal, protein, fat, carbs FROM food_db',
    'food_aliases': 'SELECT alias, product FROM food_aliases',
}.items():
    print(f'--- {table} ---')
    for row in conn.execute(sql):
        text = ' '.join(str(v or '') for v in row).lower()
        if q in text:
            print(dict(row))
conn.close()
PY
```

## Добавление продукта

Добавляй продукт только после проверки, что эквивалента нет. Перед ручной модификацией базы данных администратор обеспечивает свежий проверенный снимок (backup/restore point) через единую систему резервного копирования хоста. Прямое копирование (`cp`) живой SQLite-базы ботом запрещено, чтобы избежать повреждения данных.

```bash
$PY - <<'PY'
import os, sqlite3
path = '/opt/data/personal/nutrition/nutrition.db'
product = 'Полное название продукта'
normalized = 'короткое название'
kcal, protein, fat, carbs = 123, 1.2, 3.4, 5.6
conn = sqlite3.connect(path)
row = conn.execute(
    'SELECT id FROM food_db WHERE product=? OR normalized_name=?',
    (product, normalized),
).fetchone()
if row is None:
    cur = conn.execute(
        'INSERT INTO food_db (product, kcal, protein, fat, carbs, normalized_name) VALUES (?,?,?,?,?,?)',
        (product, kcal, protein, fat, carbs, normalized),
    )
    print('inserted', cur.lastrowid)
else:
    print('exists', row[0])
conn.commit()
conn.close()
PY
```

Перед обработкой брендированной упаковки/этикетки прочитай `references/branded-packaged-labels.md`; для консервов также `references/canned_food_labeling.md`. КБЖУ бери с упаковки, не из интернета.

## Алиасы

Добавляй короткий алиас, если пользователь регулярно использует однозначное разговорное название. Не создавай алиас по сомнительному fuzzy match и не держи несколько почти одинаковых алиасов. Если при уточнении неизвестного продукта через clarify пользователь подтвердил соответствие базовому продукту из базы (например, «яйцо сырое куриное» -> «Яйцо куриное С0 (100г)»), сохрани подтверждённый алиас в `food_aliases`, чтобы следующие записи этого продукта проходили автоматически. Соглашения: `references/alias-conventions.md`.

```bash
$PY - <<'PY'
import os, sqlite3
path = '/opt/data/personal/nutrition/nutrition.db'
conn = sqlite3.connect(path)
conn.execute(
    'INSERT OR REPLACE INTO food_aliases (alias, product) VALUES (?, ?)',
    ('короткое название', 'Полное название продукта'),
)
conn.commit()
conn.close()
PY
```

## Проверка при сбое или неизвестном результате

После verified receipt отдельная проверка не нужна. Ниже — резервная read-only проверка для диагностики; при известном `id` ищи именно его, не просто последнюю запись дня.

```bash
$PY - <<'PY'
import os, sqlite3
DATE = 'YYYY-MM-DD'
MEAL = 'snack'
path = '/opt/data/personal/nutrition/nutrition.db'
conn = sqlite3.connect('file:' + path + '?mode=ro', uri=True)
conn.row_factory = sqlite3.Row
row = conn.execute(
    'SELECT id, date, meal, total_kcal, total_protein, total_fat, total_carbs '
    'FROM nutrition WHERE date=? AND meal=? ORDER BY id DESC LIMIT 1',
    (DATE, MEAL),
).fetchone()
print(dict(row) if row else None)
if row:
    for item in conn.execute(
        'SELECT product, grams, kcal, protein, fat, carbs '
        'FROM nutrition_items WHERE nutrition_id=? ORDER BY id',
        (row['id'],),
    ):
        print(dict(item))
conn.close()
PY
```

Резервная проверка успешна, только если найдена нужная строка `nutrition` и полный ожидаемый состав `nutrition_items`.

## Просмотр съеденного и статистики

Для просмотра приёмов пищи, калорий и БЖУ используй команду `summary` CLI (без сырых inline-скриптов):

```bash
# За сегодня
$PY $CLI summary

# За конкретную дату
$PY $CLI summary --date YYYY-MM-DD

# Машинная сводка за дату (has_records/count/status/total_kcal без списка блюд)
$PY $CLI summary --date YYYY-MM-DD --summary

# Сводка за период (например, за 7 дней)
$PY $CLI summary --days 7
```

При запросе «сколько съел сегодня / за день» выводи:
1. Итоговые калории и БЖУ с сопоставлением с дневными целями из `recipe_context.py` (если цели заданы).
2. Краткий список приёмов пищи со структурой (завтрак, обед, ужин, перекусы) и составом позиций.

### Расчёт остатка КБЖУ до дневных целей

Если пользователь спрашивает «сколько осталось на сегодня» или планирует следующий приём пищи:
1. Запусти `$PY /opt/data/scripts/recipe_context.py` — он сопоставляет факт из БД с целями из `/notes/Моё здоровье/Цели и мониторинг.md` и возвращает `today.remaining`.
2. Если вопрос касается выбора еды под вечерний/дневной приём лекарств — проверь непринятые препараты в `health.db` и учти требования к приёму относительно еды из схемы (`food: before/with/after/any`).

## Исправление и удаление

1. Найди и покажи пользователю запись: `id`, дату, приём пищи, калории и состав.
2. Перечисли, что будет удалено.
3. Дождись явного подтверждения.
4. Удали запись:

```bash
$PY $CLI delete --id ID --yes
```

5. Если нужна замена, запиши исправленный полный приём пищи и снова проверь БД.

## Ответ пользователю

После обычной записи:

```text
Записал.

Перекус — 75 ккал
- лечо — 150 г
```

Если скрипт вернул напоминание о приёме лекарств (`💊 Прими ... лекарства:`), обязательно добавь этот блок и рекомендации по еде в конец ответа.
Скрипт оценивает **сумму БЖУ всей еды, записанной за последние 60 минут** (включая текущую запись), а не калории одной записи. В напоминании — только непринятые препараты `food` = with/after/any; препараты «до еды» напоминают брифы, здесь они лишь упоминаются строкой «⏰ До еды, ещё не отмечено…».
В напоминании отображаются только факты о непринятых препаратах и требования к приёму относительно еды из схемы владельца (`food: with/after/any`). Персональные эвристики по калориям и жирам отключены по умолчанию.
Вывод скрипта передавай как есть.
Если в этот период нет непринятых таблеток «с едой», напоминание не выводится.

### Подтверждение приёма таблеток
«Принял всё» → `$PY $CLI take-meds`; «принял X и Y» → `$PY $CLI take-meds --names "X, Y"`. Правила и статусы — навык `health-tracker`, раздел «Лекарства».
- **Совмещённые сообщения (еда + лекарства)**: если в одном сообщении пользователь указывает и еду, и факт приёма лекарств (напр. «перекус кофе ... принял Ко-Перинева» или «завтрак ... все таблетки выпил»), сначала запиши приём пищи через `meal`, сразу же отметь лекарства через `health.py take-meds`, и в итоговом ответе подтверди обе записи (еду и принятые лекарства), исключив только что принятые из блока напоминания.

Если после успешной записи еды подсистема напоминаний не загрузилась или завершилась ошибкой, `nutrition.py` сохраняет приём пищи, но печатает явное предупреждение в `stderr` вида `⚠️ Не удалось ... лекарства: <тип>: <ошибка>`. Не скрывай такое предупреждение и не утверждай, что проверка лекарств прошла.

Для уточнения вариантов, разрешения опечаток (например, распознавание голоса) или подтверждения интернет-поиска используй инструмент `clarify` с готовыми вариантами выбора (рекомендуемый — первым). В тексте без кнопок:

```text
Нашёл несколько вариантов: X, Y, Z. Какой использовать?
```

Если использована приблизительная интернет-оценка, явно сообщи название продукта, среднее значение на 100 г и что оценка приблизительная.
